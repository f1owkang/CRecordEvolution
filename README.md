# Charging Record

把电池健康度写在 root 管理器模块描述里的 Magisk 模块。刷入重启后自动工作，没有配置项，也没有常驻通知——数据就在模块卡片上，打开管理器就能看到。

核心是一个静态编译的 Go 二进制。稳定版用统计方法聚合；另有一个 ML 实验版会学习你这台设备的充电特征，感兴趣可以手动刷来对比。

## 安装

需要 Magisk v20.4+ / KernelSU / APatch 任一（仅 arm64）。从 [Releases](../../releases) 下载：

- `Charging_Record.zip` —— 稳定版，支持应用内更新
- `Charging_Record_ML.zip` —— 实验版（在线学习算法），不提供应用内更新，升级需手动下载刷入

在管理器里刷入 zip，音量+ 确认、音量- 取消，重启生效。两个变体互斥，后刷的替换先刷的。

KernelSU / APatch / MMRL 用户可以从管理器打开 WebUI 仪表盘，看健康度大卡、各项指标和最近的估算记录；Magisk 没有这个入口，不影响其他功能。

## 它是怎么算的

两条路，结果都写在模块描述里。

内核读数：直接读电量计的 `charge_full` 和 `charge_full_design` 相除。很多机器的内核会自己校准这个值，它是最省事也最稳的来源。

实测估算：充电时每分钟记一次电流，一次充电结束后拿充进去的电荷量除以百分比涨幅，反推整块电池现在的容量。涨幅不到 20%，或者推出来的结果超出设计容量一半到一点五倍的会话直接丢弃。

稳定版在这之上做两件事：会话期间温度必须处于 15~40 ℃，然后按指数滑动平均聚合，首个有效会话就能出结果。

ML 实验版不做硬性温度过滤，改用四分位距剔除离群会话，并用在线回归学习温度、充电倍率、起始电压对测量的系统性影响。前 30 次有效会话它和稳定版表现一致，之后逐渐引入修正——想看出区别至少要用满一个月。

已知的不准情况：边玩边充时负载电流会被算进充入电量，读数偏高，熄屏充电最准；个别厂商的电流节点单位是 mA 而不是 µA，模块靠数值大小猜单位，猜错则全错。

## 日志

运行数据存在模块目录下的 `data/battery.db`（SQLite），只保留最近 90 天，过期数据每日自动清理。有 root 终端的话可以这样翻历史：

```sh
sqlite3 /data/adb/modules/Charging_Record/data/battery.db \
  'SELECT datetime(ts, "unixepoch", "localtime"), mah FROM estimates ORDER BY ts DESC LIMIT 10;'
```

## 常见问题

**健康度超过 100% 是不是坏了？**

不是。出厂标称容量普遍保守，实际满充高于设计值很常见。

**和 AccuBattery 有什么区别？**

思路类似，都是库仑积分，但本模块以 root 直接读内核电量计，无常驻通知、无网络权限，也不依赖 Android 的电池统计接口。

**多久能看到实测估算？**

正常使用几天内出第一个数。ML 版要攒够 30 次有效会话才开始体现差异。
